# Работа над ошибками — Leseraupe 1.0 (28.10.–01.11.2026)

План для следующих приложений. Каждый пункт: **что делать → как → зачем** (и что случилось в Leseraupe).

## Порядок работы в следующий раз

| Этап | Что готово в конце | Проверка |
|---|---|---|
| 0. Бриф | 1 страница: для кого, главная функция, правила, «не делаем» | ты читаешь и говоришь «ок» |
| 1. Стиль | дизайн-система + 1 экран-образец на DE и UK | скриншот образца |
| 2. Скелет | все экраны с заглушками, навигация | обход всех экранов скриптом |
| 3. Функции | всё из брифа работает, тесты зелёные | **заморозка функций** |
| 4. Содержание | тексты/истории/данные, симуляция «30 дней» | отчёт симуляции |
| 5. Полировка | **один** пакет скриншотов → **одно** внешнее ревью → **один** список правок | второй пакет скриншотов |
| 6. Магазин | ключ, .aab, анкеты, графика, тестеры | отправка на проверку |

Новые идеи после этапа 3 — только в `IDEEN.md` на «после выпуска», не в текущую версию.

---

## 1. Бриф и список «не делаем» — до первой строки кода
- **Как:** одна страница: кто пользователь, что он делает за 1 минуту, 5–7 жёстких правил, список «не делаем в 1.0» (здесь были бы: озвучка, порядок по конкретному букварю, оплата, несколько детей).
- **Зачем:** решения «нет озвучке», «порядок как в букварях не нужен», «статус печати не нужен» приходили по ходу — и каждый раз что-то уже было сделано и переделывалось.

## 2. Стиль — первым делом, а не в конце
- **Как:** до экранов задать дизайн-систему: цвета, размеры шрифта (заголовок / текст / подсказка), кнопки (основная / второстепенная / ссылка, всегда текст по центру), карточки и их заголовки, выравнивание текста (подсказки — по ширине с переносами, короткие строки — по центру), отступы, пустые состояния. Сделать **один экран-образец** и утвердить его.
- **Зачем:** в конце ушло больше 10 кругов на одно и то же: текст по левому краю → по ширине → дыры → переносы; прыгающая кнопка «Вибрати всі»; разные заголовки карточек; кнопки в одну/две строки.
- **Проверка образца:** на узком телефоне (360 px) **и** на обоих языках сразу — украинский текст длиннее и ломает вёрстку там, где немецкий помещается.

## 3. Заморозка функций (feature freeze)
- **Как:** после этапа 3 — дата, после которой новые функции не добавляются, только исправления.
- **Зачем:** блок C (истории, «Вибрати всі», шапка листа), поздравление, плитки истории, блоки-плашки появились во время полировки — и полировку пришлось начинать заново после каждого.

## 4. Обход всех экранов скриптом — с первого дня
- **Как:** скрипт, который проходит все экраны и состояния (пусто / много данных / 10 дней / грамота / ошибки) на DE и UK и сохраняет скриншоты. Запускать в конце каждого этапа. Скрипт из этого проекта (`tour.mjs`) — взять за основу.
- **Зачем:** самые неприятные ошибки нашлись только на картинках, а не в тестах: полоса над «Ich lese!» при печати, круг после «Прочитано», двойная ссылка на грамоту, белая голова гусеницы.

## 5. Замечания — пачкой, а не по одному
- **Как:** пройти все экраны по чек-листу, записать всё в один список (номер скриншота + что не так), отдать одним сообщением. Одна волна правок → один новый пакет скриншотов → одно слияние в main.
- **Зачем:** сейчас было ~25 циклов «одно замечание → сборка → тесты → слияние → установка на телефон». Каждый цикл стоит минут 10–20, вместе — целые дни.

## 6. Внешнее ревью — один раз, на готовом, и с проверкой
- **Как:** ревью только после этапа 3 (на полном пакете скриншотов), с конкретными вопросами. Каждый пункт ревью сверять с кодом и делить: **ошибка / по ошибке ревьюера / осознанное решение / на потом**.
- **Зачем:** ревью на середине пути находили то, что ещё и так менялось. И в ревью было много неверного: «шрифт без школьной l», «ссылки на ИИ без защиты», «6:00 PM» — это эмулятор. Без проверки легко начать «чинить» несуществующее.

## 7. Содержание — отдельный этап с симуляцией
- **Как:** если ядро приложения — тексты/данные, проверять их не глазами на 1–2 листах, а симуляцией: «30 дней подряд», «все наборы букв», «повторы за неделю». Отчёт → пробелы → дописать.
- **Зачем:** повторы историй каждые 3 дня и повтор предложений на 3-й день нашлись только симуляцией, на телефоне это было бы видно через недели.

## 8. Требования магазина — в брифе, а не в конце
- **Как:** до кода решить: ID пакета, аудитория (дети → правила Families), что хранится и где, резервная копия, разрешения, нужен ли вопрос для взрослых, политика конфиденциальности. Чек-лист есть в `docs/PLAY.md`.
- **Зачем:** в Leseraupe это сделано рано — и анкеты Play Console прошли за час без переделок. Так и оставить.

## 9. Git: одна задача — одна ветка — проверить перед коммитом
- **Как:** перед каждым коммитом `git status` / `git diff --stat`; на предложения Android Studio «Upgrade…» отвечать «нет».
- **Зачем:** изменения Android Studio (обновление Gradle-плагина) незаметно попали в коммит про веб-версию и сломали сборку.

## 10. «Готово» для экрана — по одному списку
Экран готов, когда:
- [ ] DE и UK, узкий телефон (360 px) — ничего не наезжает, не обрезано
- [ ] все состояния: пусто / обычно / много данных / ошибка
- [ ] кнопки и заголовки по дизайн-системе
- [ ] на настоящем телефоне (печать, уведомления, «назад»)
- [ ] тесты зелёные, сборка зелёная

## Что взять в следующий проект готовым
Capacitor-обёртка и `DruckPlugin`, `docs/ANDROID.md`, `docs/PLAY.md` (анкеты), `privacy.html`, ключ загрузки (тот же), аккаунт разработчика, группа тестеров, скрипты скриншотов (`tour.mjs`, `store-tour.mjs`, `compose.mjs`). Лучше всего — сделать из Leseraupe пустой шаблон.

- Тесты на каждую найденную ошибку (471 к выпуску).
- Документы со статусом (`IDEEN.md`, `PLAY.md`) — всегда понятно, где мы.
- Приватность с самого начала: без аккаунтов, рекламы, трекеров.
- Проверка на своём телефоне и своём ребёнке.
